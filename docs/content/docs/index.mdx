Dispatch is a Go library for background jobs, durable workflows, cron scheduling and distributed worker coordination. You import it into your Go program. There's no separate binary, no DSL and no YAML you have to write.

Dispatch is a library, not a service. You bring your own database, HTTP server and process lifecycle, and Dispatch provides the execution plumbing.

## What it does

- Background jobs: typed handlers, queues, priority, delayed `RunAt`, retries with configurable backoff.
- Checkpointed workflows: multi-step Go functions that record each step and resume after a crash.
- A durable workflow runtime: deterministic replay with activities, timers, signals, queries and child workflows (`durable` and `durable/runtime`).
- Distributed cron: leader-elected cron, stored so every worker agrees, with runtime enable and disable.
- Dead letter queue: jobs that run out of retries land in the DLQ, where you can inspect, replay or purge them.
- Distributed workers: worker registration, heartbeats, leader election and reclaiming jobs from workers that stop heartbeating.
- Middleware: a chain for logging, tracing, metrics, panic recovery, timeouts and Forge scope injection.
- Extension hooks: opt-in lifecycle interfaces for job, workflow, cron and shutdown events.
- OpenTelemetry: metrics and tracing through the `observability` and `middleware` packages.
- Relay integration: typed webhook events at every lifecycle point through `relay_hook`.
- Pluggable storage: memory, PostgreSQL, SQLite and MongoDB through Grove, and Redis through Grove KV. Implement `store.Store` for anything else.

## Design philosophy

**Library, not framework.** Dispatch is a set of Go packages you import. You control the `main` function, the HTTP server and the process lifecycle.

**Interfaces over implementations.** Every subsystem defines a Go interface, so you can swap the storage backend without touching your jobs.

**Composable stores.** Each subsystem has its own store interface. The aggregate `store.Store` composes them all, and one backend satisfies every subsystem.

**Workflows as ordinary Go functions.** No YAML, no protobuf, no external scheduler. A workflow is a function and a step is a closure.

**TypeID everywhere.** Every entity uses a type-prefixed, K-sortable, UUIDv7-based identifier. `JobID`, `CronID` and the rest are aliases of one `id.ID` type, so the prefix (checked by the `Parse*ID` functions) is what tells them apart, not the compiler.

## Quick look

```go
package main

import (
    "context"
    "log"

    "github.com/xraph/dispatch"
    "github.com/xraph/dispatch/engine"
    "github.com/xraph/dispatch/job"
    "github.com/xraph/dispatch/store/memory"
)

type EmailInput struct {
    To      string `json:"to"`
    Subject string `json:"subject"`
}

var SendEmail = job.NewDefinition("send_email",
    func(ctx context.Context, input EmailInput) error {
        log.Printf("sending to %s: %s", input.To, input.Subject)
        return nil
    },
)

func main() {
    ctx := context.Background()

    d, err := dispatch.New(dispatch.WithStore(memory.New()))
    if err != nil {
        log.Fatal(err)
    }

    eng, err := engine.Build(d)
    if err != nil {
        log.Fatal(err)
    }
    engine.Register(eng, SendEmail)

    if err := d.Start(ctx); err != nil {
        log.Fatal(err)
    }
    defer d.Stop(ctx)

    if _, err := engine.Enqueue(ctx, eng, "send_email", EmailInput{
        To:      "user@example.com",
        Subject: "Welcome!",
    }); err != nil {
        log.Fatal(err)
    }
}
```
