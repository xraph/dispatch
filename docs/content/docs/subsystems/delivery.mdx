---
title: Workflows
description: Durable multi-step functions with checkpointing, parallel execution, and event waiting.
---

Workflows are durable, multi-step Go functions. Dispatch checkpoints each completed step so that if the process restarts mid-workflow, execution resumes after the last completed step instead of starting over.

## Defining a workflow

```go
import "github.com/xraph/dispatch/workflow"

type OrderInput struct {
    OrderID      string  `json:"order_id"`
    Amount       float64 `json:"amount"`
    CustomerID   string  `json:"customer_id"`
    PaymentToken string  `json:"payment_token"`
}

var ProcessOrder = workflow.NewWorkflow("process_order",
    func(wf *workflow.Workflow, input OrderInput) error {
        if err := wf.Step("validate", func(ctx context.Context) error {
            return validateOrder(ctx, input.OrderID)
        }); err != nil {
            return err
        }

        if err := wf.Step("charge", func(ctx context.Context) error {
            return chargeCard(ctx, input.PaymentToken, input.Amount)
        }); err != nil {
            return err
        }

        return wf.Step("fulfill", func(ctx context.Context) error {
            return fulfillOrder(ctx, input.OrderID)
        })
    },
)
```

## Registering a workflow

```go
engine.RegisterWorkflow(eng, ProcessOrder)
```

## Starting a workflow

You start a workflow by name:

```go
run, err := engine.StartWorkflow(ctx, eng, "process_order", OrderInput{
    OrderID: "ORD-001",
    Amount:  99.99,
})
```

`StartWorkflow` runs the handler in the calling goroutine and returns the `*workflow.Run` once it finishes or fails. Runs left in `running` after a crash are resumed when the engine starts again.

## Steps

`wf.Step(name, fn)` runs `fn` with the workflow's context and saves a checkpoint when it succeeds. When the workflow runs again after a crash or restart, a step that already has a checkpoint is skipped.

A step that was in flight when the process died has no checkpoint, so it runs again. Steps are at-least-once, so make their side effects idempotent. `workflow.StepWithResult(wf, name, fn)` also checkpoints the step's return value (gob-encoded) and hands back the cached value on resume.

## Parallel steps

Run independent steps concurrently. The first argument names the group:

```go
if err := wf.Parallel("notify",
    func(ctx context.Context) error { return sendConfirmationEmail(ctx, input.CustomerID) },
    func(ctx context.Context) error { return updateInventory(ctx, input.OrderID) },
    func(ctx context.Context) error { return notifyWarehouse(ctx, input.OrderID) },
); err != nil {
    return err
}
```

If any step fails, `Parallel` cancels the others' context and returns the first error. Each sub-step gets its own checkpoint (`parallel:<group>:<index>`), and a group checkpoint marks the whole group done.

## Waiting for events

A workflow can pause until a named event arrives:

```go
evt, err := wf.WaitForEvent("payment.confirmed", 24*time.Hour)
if err != nil {
    return err
}
if evt == nil {
    return errors.New("payment not confirmed in time")
}
```

On timeout, `WaitForEvent` returns `nil, nil` and checkpoints that. Events are matched by name, not by run, so put something run-specific in the name if several runs wait at once. `WaitForAll`, `WaitForAny` and `WaitForMatch` wait on several names or filter by payload.

To publish the event from outside, use the engine's event bus:

```go
_, err := eng.EventBus().Publish(ctx, "payment.confirmed", payloadJSON, "", "")
```

The last two arguments are the app and org scope IDs.

## Sleeping

Pause for a duration. The sleep is checkpointed, so a resumed run doesn't sleep again:

```go
if err := wf.Sleep("cool-off", 30*time.Minute); err != nil {
    return err
}
```

## Compensation and child workflows

`wf.StepWithCompensation(name, execute, compensate)` pushes `compensate` onto a stack when `execute` succeeds. When the workflow fails later, the compensations run in reverse order (the saga pattern). `workflow.RunChild[T, R](wf, name, input)` starts a child workflow and blocks for its result, and `workflow.SpawnChild` starts one without waiting.

## Run states

| State | Meaning |
|-------|---------|
| `running` | Workflow is executing |
| `completed` | All steps finished successfully |
| `failed` | The handler returned an error |
