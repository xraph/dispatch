---
title: Observability
description: Metrics and OpenTelemetry tracing for Dispatch.
---

Dispatch gives you two layers of observability, and `engine.Build` turns both on for you:

1. System-wide counters through `observability.MetricsExtension`, one per lifecycle event.
2. Per-job tracing and metrics through the `Tracing` and `Metrics` middleware in the default stack.

You choose where they report with two engine options:

```go
eng, err := engine.Build(d,
    engine.WithTracerProvider(tp),        // an OpenTelemetry trace.TracerProvider
    engine.WithMetricFactory(factory),    // a go-utils metrics.MetricFactory
)
```

Without `WithTracerProvider`, the tracing middleware uses the global OpenTelemetry tracer provider. Without `WithMetricFactory`, Dispatch creates its own go-utils metrics collector named `dispatch`. The Forge extension passes the app's metrics, so counters show up next to the rest of your app's.

## System-wide counters

`engine.Build` registers an `observability.MetricsExtension` built on the metric factory. Don't register another one, or every event counts twice. If you build one yourself for another engine, use `observability.NewMetricsExtension()` or `observability.NewMetricsExtensionWithFactory(factory)`.

### Counters recorded

| Event | Counter |
|-------|---------|
| Job enqueued | `dispatch.job.enqueued` |
| Job completed | `dispatch.job.completed` |
| Job failed | `dispatch.job.failed` |
| Job retrying | `dispatch.job.retried` |
| Job moved to the DLQ | `dispatch.job.dlq` |
| Workflow started | `dispatch.workflow.started` |
| Workflow completed | `dispatch.workflow.completed` |
| Workflow failed | `dispatch.workflow.failed` |
| Cron fired | `dispatch.cron.fired` |

The counters carry no labels. How the dotted names appear in your backend depends on the exporter (Prometheus, for example, turns dots into underscores).

## Per-job tracing

Each job execution creates a span named `dispatch.job.execute` with these attributes:

- `dispatch.job.id`
- `dispatch.job.name`
- `dispatch.queue`
- `dispatch.retry_count`
- `dispatch.scope.app_id`
- `dispatch.scope.org_id`

When the handler returns an error, the span records it and gets an error status.

## Per-job metrics

The metrics middleware records a histogram `dispatch.job.duration` (seconds) and a counter `dispatch.job.executions`. Neither has labels.

## Building the middleware yourself

`middleware.Tracing()`, `middleware.TracingWithTracer(tracer)`, `middleware.Metrics()` and `middleware.MetricsWithFactory(factory)` are exported if you compose a chain outside the engine. Inside an engine they're already in the default stack, so adding them with `engine.WithMiddleware` records everything twice.
