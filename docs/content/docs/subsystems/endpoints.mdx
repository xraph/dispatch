---
title: Cron
description: Distributed cron scheduling with leader election and per-tenant support.
---

The `cron` package provides distributed cron scheduling. Only the cluster leader fires cron entries, so a tick enqueues one job even when several Dispatch instances are running.

## Registering a cron

Use `engine.RegisterCron` at startup. A cron names a registered job and the payload to enqueue on each tick:

```go
type ReportInput struct {
    Format string `json:"format"`
}

var GenerateReport = job.NewDefinition("generate_report",
    func(ctx context.Context, input ReportInput) error {
        return generateDailyReport(ctx, input.Format)
    },
)

engine.Register(eng, GenerateReport)

// Run every day at 9 AM
err := engine.RegisterCron(ctx, eng, &cron.Definition[ReportInput]{
    Name:     "daily-report",
    Schedule: "0 9 * * *",
    JobName:  "generate_report",
    Payload:  ReportInput{Format: "pdf"},
})
```

The entry is stored. Registering a name that already exists returns nil and leaves the stored entry alone, so you can call `RegisterCron` on every start. That also means changing the schedule in code doesn't update an existing entry. `RegisterCron` returns an error for an invalid expression or one that never fires (30 February). Set `Queue` on the definition to enqueue onto another queue.

## Schedule format

Dispatch parses standard 5-field cron expressions with `robfig/cron/v3`:

```
* * * * *
| | | | |
| | | | +-- day of week (0 to 6, Sunday = 0)
| | | +---- month (1 to 12)
| | +------ day of month (1 to 31)
| +-------- hour (0 to 23)
+---------- minute (0 to 59)
```

Descriptors such as `@hourly`, `@daily` and `@every 30s` work too, and a `CRON_TZ=` prefix sets the time zone.

Common expressions:

| Expression | Meaning |
|-----------|---------|
| `* * * * *` | Every minute |
| `0 * * * *` | Every hour |
| `0 9 * * 1-5` | Weekdays at 9 AM |
| `0 0 1 * *` | First of each month at midnight |
| `@hourly` | Every hour (alias) |
| `@daily` | Every day at midnight (alias) |

## Enable and disable

Cron entries can be toggled at runtime with `eng.EnableCron(ctx, cronID)` and `eng.DisableCron(ctx, cronID)`, or through the admin API:

```bash
POST /dispatch/v1/crons/:cronId/enable
POST /dispatch/v1/crons/:cronId/disable
```

Disabled entries are skipped by the scheduler without being deleted.

## Admin API

Paths are relative to the extension's base path (`/dispatch` by default).

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/v1/crons` | List all cron entries |
| `GET` | `/v1/crons/:cronId` | Get cron entry |
| `POST` | `/v1/crons/:cronId/enable` | Enable |
| `POST` | `/v1/crons/:cronId/disable` | Disable |
| `DELETE` | `/v1/crons/:cronId` | Delete |
| `POST` | `/v1/crons/:cronId/trigger` | Enqueue the job now |

## Extension hook

When a cron fires and a job is enqueued, the `ext.CronFired` hook is called:

```go
type CronFired interface {
    OnCronFired(ctx context.Context, entryName string, jobID id.JobID) error
}
```
