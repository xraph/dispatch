title: Forge Extension

The `github.com/xraph/dispatch/extension` package plugs Dispatch into a [Forge](https://github.com/xraph/forge) app. It picks up a Grove database from the container (or the store you pass), runs the store migrations on start, builds the engine, provides `*engine.Engine` through DI and mounts the REST admin API.

## Setup

```go
import (
    "context"
    "net/http"

    "github.com/xraph/dispatch/cron"
    "github.com/xraph/dispatch/engine"
    dispatchext "github.com/xraph/dispatch/extension"
    "github.com/xraph/forge"
    _ "github.com/xraph/grove/drivers/pgdriver"
    groveext "github.com/xraph/grove/extension"
)

jobs := dispatchext.New(
    dispatchext.WithConcurrency(8),
    dispatchext.WithQueues([]string{"default", "critical"}),
)

app := forge.NewApp(forge.AppConfig{
    Name:        "accounts",
    HTTPAddress: ":8080",
    Extensions: []forge.Extension{
        groveext.New(groveext.WithDSN("postgres", "postgres://localhost:5432/accounts?sslmode=disable")),
        jobs,
    },
})

err := app.RegisterHook(forge.PhaseAfterRegister, func(ctx context.Context, _ forge.App) error {
    eng := jobs.Engine()
    engine.Register(eng, SendWelcome)

    return engine.RegisterCron(ctx, eng, &cron.Definition[Signup]{
        Name:     "nightly-digest",
        Schedule: "0 2 * * *",
        JobName:  "send_welcome",
        Payload:  Signup{Email: "team@example.com"},
    })
}, forge.LifecycleHookOptions{Name: "register-jobs"})
```

`jobs.Engine()` is nil until the extension has registered, which is why job registration sits in a `PhaseAfterRegister` hook. The extension declares a dependency on the `grove` extension, so Forge registers Grove first. If you don't run Grove, Forge skips that dependency.

Forge calls `Start` when the app starts (that's when migrations run and workers begin polling) and `Stop` on shutdown.

## Extension options

| Option | Purpose | Default |
|--------|---------|---------|
| `WithStore(s)` | Use this store instead of a Grove one | none |
| `WithGroveDatabase(name)` | Resolve a `*grove.DB` from DI by name (`""` for the default) | auto-discovers the default `*grove.DB` |
| `WithGroveKV(name)` | Resolve a Grove `*kv.Store` from DI and use the Redis store | off |
| `WithKVKeyPrefix(prefix)` | Prefix every Redis key (Grove KV path only) | `""` |
| `WithConcurrency(n)` | Max concurrent jobs | `10` |
| `WithQueues(q)` | Queues to poll | `["default"]` |
| `WithPollInterval`, `WithMaxPollInterval`, `WithHeartbeatInterval`, `WithStaleJobThreshold`, `WithWorkerStoreCallTimeout` | Worker tuning | see [Configuration](/docs/concepts/configuration) |
| `WithCronTickInterval`, `WithCronLeaderTTL`, `WithCronLockTTL`, `WithCronRefreshInterval`, `WithCronStoreCallTimeout` | Cron tuning | subsystem defaults |
| `WithBasePath(p)` | Prefix for the REST routes | `"/dispatch"` |
| `WithDisableRoutes()` | Mount no HTTP routes | off |
| `WithDisableMigrate()` | Skip store migrations on start | off |
| `WithExtension(x)` | Register a lifecycle extension | none |
| `WithMiddleware(m)` | Add job middleware | none |
| `WithBackoff(b)` | Retry backoff strategy | exponential with jitter |
| `WithLogger(l)` | A go-utils `log.Logger` for the dispatcher | the app's logger |
| `WithDWP(opts...)` | Turn on the Dispatch Wire Protocol | off |
| `WithRemoteSecurity(auth, boundary)` | Your own authenticator and boundary for the admin routes | Forge auth plus Warden |
| `WithOperatorSecurity(cfg)` | Which auth providers and Warden resource the stock security uses | none |
| `WithConfig(cfg)`, `WithRequireConfig(bool)` | Set the whole `Config`, or fail when no YAML config exists | |

The resource, artifact and durable runtime options (`WithResources`, `WithArtifacts`, `WithDurableWorkflows` and friends) are covered on their own pages.

## Migrations

`Start` runs `Migrate` on the store unless you pass `WithDisableMigrate()` or set `disable_migrate: true`:

```go
jobs := dispatchext.New(
    dispatchext.WithGroveDatabase(""),
    dispatchext.WithDisableMigrate(),
)
```

## Getting the engine

The extension provides `*engine.Engine` in the container, so a handler can inject it:

```go
err = app.Router().POST("/signup", func(ctx forge.Context) error {
    eng, err := forge.Inject[*engine.Engine](app.Container())
    if err != nil {
        return err
    }

    j, err := engine.Enqueue(ctx.Context(), eng, "send_welcome", Signup{Email: "ada@example.com"})
    if err != nil {
        return err
    }

    return ctx.JSON(http.StatusAccepted, map[string]string{"job_id": j.ID.String()})
})
```

You can also keep the `*extension.Extension` around and call `jobs.Engine()` once the app has registered.

## Grove integration

When your app runs the [Grove extension](https://github.com/xraph/grove), Dispatch resolves a `*grove.DB` from the container and builds the matching store from the driver name: `pg` gives the PostgreSQL store, `sqlite` the SQLite store and `mongo` the MongoDB store. Any other driver fails registration.

### The default database

If Grove registers one database (or a default in multi-DB mode), you don't need an option at all: the extension finds the default `*grove.DB` on its own. `WithGroveDatabase("")` does the same thing but fails registration when there's no default database, instead of moving on.

### A named database

```go
jobs := dispatchext.New(
    dispatchext.WithGroveDatabase("jobs"),
)
```

### A Grove KV store

`WithGroveKV` resolves a `*kv.Store` and wraps it in the Redis store:

```go
jobs := dispatchext.New(
    dispatchext.WithGroveKV("dispatch-kv"),
)
```

When several Dispatch instances share one Redis, give each its own key prefix. Every key, stream and pub/sub channel the store touches goes under it (`ws_acme:dispatch:job:<id>`), so instances never see each other's queues, cron locks or leadership. Leave it empty for a single instance and the keys stay `dispatch:*`:

```go
jobs := dispatchext.New(
    dispatchext.WithGroveKV("dispatch-kv"),
    dispatchext.WithKVKeyPrefix("ws_acme:"),
)
```

### How the store is chosen

The extension picks its store during `Register`:

1. Grove database, if you called `WithGroveDatabase` or set `grove_database`.
2. Otherwise Grove KV, if you called `WithGroveKV` or set `grove_kv`.
3. Otherwise the default `*grove.DB`, if one is in the container.
4. Otherwise the store you passed with `WithStore`.

There's no in-memory fallback. With none of these, registration fails with `dispatch: no store configured`. A store found through Grove is applied after `WithStore`, so if a Grove database is in the container it wins even when you also passed `WithStore`.

## YAML configuration

The extension reads `extensions.dispatch` first and falls back to a top-level `dispatch` key:

```yaml
extensions:
  dispatch:
    base_path: /dispatch
    grove_database: jobs
    disable_routes: false
    disable_migrate: false
    enable_dwp: false
```

Or with the Redis store:

```yaml
dispatch:
  grove_kv: dispatch-kv
  key_prefix: "ws_acme:"
```

### Configuration reference

| Field | YAML key | Type | Default | Description |
|-------|----------|------|---------|-------------|
| `BasePath` | `base_path` | `string` | `"/dispatch"` | Prefix for the REST routes, which live under `<base_path>/v1` |
| `GroveDatabase` | `grove_database` | `string` | `""` | Name of the `*grove.DB` to resolve from DI |
| `GroveKV` | `grove_kv` | `string` | `""` | Name of the Grove `*kv.Store` to resolve from DI |
| `KeyPrefix` | `key_prefix` | `string` | `""` | Prefix for every Redis key the Grove KV store writes |
| `DisableRoutes` | `disable_routes` | `bool` | `false` | Skip HTTP route registration |
| `DisableMigrate` | `disable_migrate` | `bool` | `false` | Skip migrations on start |
| `EnableDWP` | `enable_dwp` | `bool` | `false` | Turn on the Dispatch Wire Protocol |
| `DWPBasePath` | `dwp_base_path` | `string` | `""` (DWP uses `/dwp`) | Prefix for the DWP endpoints |
| `Resources` | `resources.*` | | off | Resource-aware admission |
| `Artifacts` | `artifacts.*` | | off | The artifact plane over a Trove store |
| `Execution` | `execution.subprocess.*` | | off | The subprocess execution rung |
| `Durable` | `durable.*` | | off | The history-based durable runtime |
| `Security` | `security.installation_id`, `policy_tenant`, `providers` | | | Which auth providers and Warden resource the admin routes use |

Worker tuning (concurrency, queues, poll and heartbeat intervals, cron timings) is code-only. Use the `With*` options above. A `dispatch:` block nested under the extension key (`extensions.dispatch.dispatch.concurrency` and so on) parses without error, but nothing reads it, so it has no effect.

## Admin routes and security

With routes on, the extension mounts the admin API under `<base_path>/v1`: `/dispatch/v1/jobs`, `/dispatch/v1/workflows/runs`, `/dispatch/v1/dlq`, `/dispatch/v1/crons`, `/dispatch/v1/stats` and their actions. Every route authenticates through the Forge auth extension and authorizes with [Warden](https://github.com/xraph/warden) by default, so your app needs both registered. Pass `WithRemoteSecurity` to bring your own authenticator and boundary, or `WithDisableRoutes()` to mount nothing. See the [HTTP API reference](/docs/api-reference/http-api) for every route.

## Without Forge

The extension only works inside a Forge app: `Start` fails with `dispatch: extension not initialized` until Forge has called `Register`. Outside Forge, build the dispatcher and engine yourself as shown in [Getting Started](/docs/getting-started).
